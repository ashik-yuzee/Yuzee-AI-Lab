1. Executive Summary

🔴

Production token cost grows quadratically per conversation — not linearly. At a 63,000-token instruction, every turn from the 4th onward is billed at Gemini's premium rate, and the conversation hard-fails at turn 17. This is not a theoretical risk — it is the most likely explanation for reported "chat stops working on long sessions" support tickets.

⚠️

The leading latency cause (the ~10 s users wait) is request amplification: up to 4 sequential model calls per user message, each carrying the full (and growing) conversation memory. This compounds the token problem directly into perceived latency.

⚠️

A shared "default" conversation ID on one code path (GeminiClient.java:253) means one student's history can surface in another student's context. This is a privacy and correctness defect independent of all cost issues.

The Yuzee AI Token Lab was built to validate and demonstrate the correct architecture for all of these problems. It implements: a token-budget context assembler with stable prefix ordering, true SSE streaming, per-turn telemetry, greeting bypass (zero tokens for greetings), per-IP rate limiting, and per-bubble model/latency/token display.

The single most important implementation action is Fix A: deliver the counselling instruction via the system channel, not the user channel. This is a 4-line change that removes the quadratic term entirely and unlocks prefix caching — delivering an estimated 5–22× cost reduction depending on instruction size.

4. Defect D1 — Quadratic Token Growth Critical

🔴

Root cause: Yuzee delivers the ~63,000-token counselling instruction via .user(instructionTextFromMongo) (GeminiClient.java:76, 149, 253). Spring AI's MessageChatMemoryAdvisor persists the last user message to memory on every turn. That last user message is the freshly-loaded instruction. So a full copy of the instruction is written into history on every single turn — and the entire accumulated history is re-transmitted on every subsequent turn.

The Mechanism (Proven from Spring AI 1.0.0 GA Source)

// MessageChatMemoryAdvisor.before() — source jar verified live
public ChatClientRequest before(ChatClientRequest req, AdvisorChain chain) {
    List<Message> memoryMessages = this.chatMemory.get(conversationId);

    // Step 2: prepends entire retained window to outgoing request
    List<Message> processed = new ArrayList<>(memoryMessages);
    processed.addAll(req.prompt().getInstructions());

    // Step 4: persists last user message to memory
    UserMessage userMsg = processedReq.prompt().getUserMessage(); // ← reverse scan returns the INSTRUCTION
    this.chatMemory.add(conversationId, userMsg);                 // ← instruction saved to DB every turn
    return processedReq;
}

Prompt.getUserMessage() scans backwards and returns the last user message — which in Yuzee's call is the freshly-loaded MongoDB instruction text. The actual student utterance is injected elsewhere, so the student's message is NOT what gets persisted — the instruction blob is.

The Cost Growth Model

Under the current design, turn N sends the whole retained history plus a fresh instruction copy:

sent(N)       = N·P + (N−1)·A
cumulative(N) = P·N(N+1)/2 + A·N(N−1)/2

where: P = instruction tokens per turn, A = average assistant reply (~800 tokens)

The N(N+1)/2 term is quadratic. Token cost per conversation does not grow linearly with conversation length — it accelerates.

Instruction size (P) Turn 1 Turn 3 Turn 5 Turn 10 Cumulative @10 Exceeds 200k at Hard-fails at
63,000 63,000 190,600 318,200 637,200 3,501,000 Turn 4 Turn 17
20,000 20,000 61,600 103,200 207,200 1,136,000 Turn 10 Turn 51
8,000 8,000 25,600 43,200 87,200 476,000 Turn 23 Turn 120
⚠️

At P=63k: Every turn from the 4th onward is billed at Gemini's premium rate (input above 200k tokens). The premium applies to the entire request, not just the excess. The conversation hard-fails with a context-window error at turn 17 — long before the maxMessages(100) safety valve ever engages (which first evicts at turn 51).

The Framework Already Has the Fix — Production Opted Out

MessageWindowChatMemory.process() gives SystemMessage three privileges that exist precisely for large standing instructions:

  • Deduplicated by replacement — only ever one copy in memory (hasNewSystemMessage drops the prior system message)
  • Exempt from eviction — never removed during trim (message instanceof SystemMessage skips the eviction loop)
  • Pinned to the front — system messages always appear first in the list, creating a stable cacheable prefix

Yuzee uses .user() and forfeits all three. Spring AI already implements the fix. Production opted out by choosing the wrong message type.

❌ Current (Production)
chatClient.prompt()
  .user(instructionFromMongo) // 63k tokens
  // → saved to memory EVERY TURN
  // → replayed EVERY SUBSEQUENT TURN
  .advisors(...)
  .stream();
✅ Fix (4 Lines)
chatClient.prompt()
  .system(stableInstruction) // one copy, ever
  // → Vertex routes to withSystemInstruction()
  // → cache-eligible prefix
  .user(actualStudentMessage)
  .advisors(...)
  .stream();

5. Defect D2 — Memory Bounded by Message Count, Not Tokens Critical

MessageWindowChatMemory.maxMessages(100) (YuzeeGeminiAdapterApplication.java:63) counts messages, not tokens. One hundred 60-token messages and one hundred 63,000-token messages are treated identically.

🔴

This control cannot bound spend, because spend is denominated in tokens and the control is denominated in messages. The first eviction happens at turn 51 (100 messages = 50 turns). At P=63k, the conversation hard-fails at turn 17 — the safety valve is set 34 turns beyond the failure point.

What the Token Lab Does Instead

The lab uses a token budget context assembler. The default budget is 2,000 context tokens (adjustable per conversation). The assembler:

  • Measures the token cost of each component (system instruction, career context, summary, recent turns, current message)
  • Keeps recent turns until the budget is exhausted — evicting oldest dialogue pairs first
  • Never evicts the stable system instruction
  • Shows a real breakdown (System: X tokens · Memory: Y tokens · Message: Z tokens) in the UI before each send

For production, the equivalent is a custom TokenBudgetChatMemory implementing Spring AI's 4-method ChatMemory interface:

public interface ChatMemory {
    void add(String conversationId, List<Message> messages);
    List<Message> get(String conversationId);
    void clear(String conversationId);
}

// TokenBudgetChatMemory should:
// - preserve SystemMessage unconditionally
// - evict oldest user+assistant pairs (in whole pairs, not half-exchanges)
// - stop evicting once the remaining window fits the token budget
// - never count the system instruction against the budget

6. Defect D3 — Front-First Eviction Destroys Cacheable Prefix High

MessageWindowChatMemory.process() evicts from the front of the message list when the window overflows. In production, the instruction blobs accumulate at the front (as user messages). When eviction finally does engage, it removes the oldest instruction copies — which happen to be at the front of the conversation history.

Even if the instruction were correctly delivered as a SystemMessage, front-first eviction would destroy the conversation's oldest, most contextually valuable turns first. The correct eviction order is oldest dialogue turns (the volatile end), leaving the stable system instruction and recent exchanges intact.

ℹ️

This defect becomes irrelevant once D1 and D2 are fixed. With the instruction as a system message (exempt from eviction) and memory bounded by tokens (not messages), eviction only fires on genuinely long conversations — and at that point, oldest dialogue pairs are the correct things to remove.

7. Defect D4 — Zero Telemetry: The Meta-Cause Critical

🔴

This is why everything else went unnoticed. Production captures no promptTokenCount, no totalTokenCount, no usage metadata of any kind. A conversation that costs 50× another produces identical logs. No APM, no Grafana, no structured per-turn metrics exist. Every defect above is structurally invisible.

The fix is a single getUsage() call on the ChatResponse:

ChatResponse response = chatClient.prompt()...call();
Usage usage = response.getMetadata().getUsage();
long inputTokens  = usage.getPromptTokens();
long outputTokens = usage.getCompletionTokens();
long totalTokens  = usage.getTotalTokens();

// Persist per conversation and per turn.
// The single regression test for this entire class of defect:
// promptTokenCount(turn 10) / promptTokenCount(turn 1)
// Today: ~10x.  After fixes A + C: should approach ~1.1x.
⚠️

Do this first, before any other fix. Without a baseline measurement, every other claim — including the projections in this document — is unfalsifiable. The token-growth ratio at turn 10 vs turn 1 is the cleanest single number that tells you whether the quadratic defect is present and whether fixes are working.

What the Token Lab Provides

Every assistant bubble in the lab displays:

  • Model chip — which model handled this specific turn (color-coded by family)
  • Latency — total round-trip time in seconds for this turn
  • Token pill — In X · Out Y · Think Z · Cache N · Total — clickable for full breakdown
  • Compaction banner — when context was optimised, showing tokens before → after
  • Session stats — cumulative totals in the header (In · Out · Saved)

The server records timeline.preProviderMs, timeline.providerTtftMs, timeline.totalLatencyMs per turn, enabling end-to-end latency attribution that production has never had.

8. Defect D5 — Request Amplification: The Leading Latency Cause Critical

This is the highest-confidence explanation for the ~10 s latency users experience. One user message can trigger up to 4 sequential model calls, each carrying the full (and growing) conversation memory:

CallTriggerFrequencyCarries full memory?
Main conversationUser messageAlways (1)Yes
MINI_PATHWAYhandleResponse sees status PASS (PromptPlaceholderReplacer.java:67)0–1Yes — same conversationId
nextPromptNext action in ACTION_FLOW (:80)0–1Yes — same conversationId
Title generationfinalizeConversationAsync on completion (GeminiClient.java:149)0–1Yes — advisor attached
🔴

Three sequential calls at ~3 s each = ~9–10 s, matching the reported symptom exactly. This also means token cost is multiplied by up to 4× per user message, compounding on top of the quadratic growth from D1. This is multiplicative with the token problem — not an alternative to it.

The fix is Optimisation M from the audit: eliminate avoidable chained calls. Specifically:

  • Title generation does not need a full-model call with complete conversation memory — a lightweight summarisation prompt with only the last 2 turns is sufficient
  • MINI_PATHWAY and nextPrompt chained calls should be parallelised or made conditional on cheaper classification signals
  • Internal administrative calls (not visible to the user) should use a lightweight model (e.g. flash-lite), not the counselling model
ℹ️

Decisive test (5 minutes, no code change): Capture a browser HAR for a typical chat request. If the response arrives as a single blob at the end, streaming is not reaching the user. Count the number of Vertex AI invocations sharing one ai_request_id — this directly measures the amplification factor.

9. Defect D6 — Buffered Response (stream=false) High

The production client makes the main chat request as:

POST .../text-refinement?conversation_id=<id>&stream=false   (gemini-fixes.service.ts:405-418)

Two Accept headers coexist in the client — text/event-stream (:271) and application/json (:417). The stream=false path means the server waits for the complete response from Vertex AI before beginning to return anything to the browser.

⚠️

This converts "TTFT 2 s + generation 5 s" into 7 s of blank screen — sufficient on its own to produce a perceived ~10 s latency even with a fast model. Fixing this alone would be the largest perceived-latency improvement at the lowest risk.

What the Token Lab Does

The lab uses true SSE streaming (generateContentStream from @google/genai) with the following event sequence:

  • start — immediately confirms the server received the request
  • status — shows "Generating..." while the model is thinking
  • delta — each token chunk as it arrives from Gemini
  • structured — complete Protocol v1.3 object when streaming ends
  • usage — token and timing data after the response completes
  • done — stream closed

The user sees the first visible content in ~1–2 s even for a long response. The total generation time is the same — only the perceived wait changes.

The fix for production: Pass stream=true and ensure PromptPlaceholderReplacer.handleResponse() (which currently parses the complete response for a status field before deciding chained calls) is refactored to work on the streaming path. The chained-call decision must not require a complete response to be buffered.

10. Defect D7 — Shared "default" Conversation Critical (Privacy)

GeminiClient.java:253 calls sendSingleMessage without the CONVERSATION_ID advisor parameter. The bean-level defaultAdvisors still attach memory, so the call falls back to ChatMemory.DEFAULT_CONVERSATION_ID = "default" — a single shared conversation for every user.

🔴

One student's counselling history can surface in another student's context. This is a privacy and correctness defect independent of all cost issues. The shared conversation accumulates without limit as all users' messages are appended to the same history.

Fix: Pass the authenticated user's conversation ID on every call path. This is a one-line change at GeminiClient.java:253 — the most urgent fix that should not wait behind a cost programme.

// Current (broken) — falls back to "default" shared conversation
chatClient.prompt()
    .user(...)
    .stream(); // No CONVERSATION_ID parameter

// Fixed
chatClient.prompt()
    .user(...)
    .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, authenticatedUserId + ":" + sessionId))
    .stream();

11. Secondary Issues

D8 — Database Write Amplification

JdbcChatMemoryRepository.saveAll() (Spring AI 1.0.0 source, verified live):

this.transactionTemplate.execute(status -> {
    deleteByConversationId(conversationId);        // delete ALL rows
    this.jdbcTemplate.batchUpdate(...);            // reinsert entire history
    return null;
});

Every turn deletes every row for the conversation and re-inserts the entire retained history. With instruction-sized blobs accumulating, each turn rewrites megabytes of text to RDS. This grows on the same quadratic curve as the token cost, and shows up as database load, transaction duration, and write IOPS. It was a contributing factor in the 2026-08-14 outage.

Fix: Implement append-only persistence (Optimisation Q from the audit) — store only new messages per turn rather than deleting and reinserting the full window. This reduces DB writes from O(N) per turn to O(1).

D9 — Unresolved Model Identity

The model is configured via a non-standard property key vertex.ai.gemini.chat.options.model — not the Spring AI standard key. The last verified value was gemini-2.5-pro, but the brief states the team may have changed it to gemini-3.5-flash-lite. These are fundamentally different models: 2.5 Pro is a high-reasoning model with default thinking enabled, materially slower and more expensive. If the model has not changed, thinking tokens are being consumed unbounded on every counselling turn with no budget set and no measurement.

Decisive test (30 seconds): Read application.properties:72 on the live deploy. The answer reframes the entire latency audit.

D10 — Mongo Prompt Fetch Per Request (No Cache)

Prompts are fetched from MongoDB via getPromptByAction(action) on every single request. No application-level cache exists. The document is unversioned (no version, status, or checksum field), so a safe cache-by-hash strategy cannot be applied without a schema migration. Query duration and document size are currently unmeasured.

Fix: Add a checksum field to the Prompt document. Cache the fetched prompt in a local ConcurrentHashMap keyed by (action, checksum). Invalidate on checksum change. This eliminates the Mongo round-trip on every request.

D11 — 91-Minute Read Timeout

setReadTimeout(5500000) (YuzeeGeminiAdapterApplication.java:77–78) — approximately 91 minutes. This does not contribute to latency but removes all timeout-based protection: a hung provider call would occupy a thread indefinitely rather than failing fast.

D12 — Blocking I/O on Reactive Threads (Threading Starvation Risk)

The stack is Spring MVC with Reactor Flux on an SSE endpoint, while chat memory uses blocking JDBC and prompts use the blocking Mongo driver. Blocking I/O on reactive execution paths is a recognised thread-starvation risk. Whether it materialises under current load is a hypothesis — thread-pool metrics would settle it.

12. How the Token Lab Solves Each Problem

Problem: Quadratic token growth (D1)

Lab solution: Stable system instruction + ordered context assembly.

The lab's YuzeeRequestAssembler builds every request in a fixed order: system instruction first (byte-identical per turn), then career context, then a conversation summary (if compacted), then the last 4 turns, then the current message. The system instruction is sent as the systemInstruction field of the Gemini API request — the field the provider treats as the stable, cache-eligible header.

Because the system instruction is not in the conversation history, it is sent once per request but never accumulates across turns. Cost grows linearly with dialogue turns — not quadratically with instruction copies.

Problem: Memory bounded by message count (D2)

Lab solution: Token budget context assembler.

The lab's context assembler accepts a contextBudget (default 2,000 tokens). Before assembling the request, it estimates the token cost of each component and drops oldest dialogue turns until the total fits within the budget. This means the maximum context cost is bounded regardless of how long the conversation runs — a 50-turn conversation costs the same as a 5-turn conversation once it stabilises at the budget.

Problem: Zero telemetry (D4)

Lab solution: Per-turn telemetry on every response.

The @google/genai SDK returns usageMetadata on every generateContent call. The lab extracts promptTokenCount, candidatesTokenCount, thoughtsTokenCount, and cachedContentTokenCount, computes total as uncachedInput + output + thinking, and attaches all of it to the SSE response as a usage event. These numbers appear on each chat bubble so the developer sees exactly what each turn cost.

Problem: Perceived latency from buffering (D6)

Lab solution: True SSE streaming from first token.

The lab calls model.generateContentStream() and pipes each delta event directly to the browser as a Server-Sent Event. The React frontend renders each chunk as it arrives. First visible content appears in approximately 1–2 s; the total generation time is identical but the user experience is completely different.

Problem: Zero-token greeting handling

Lab solution: Message classification before any model call.

// YuzeeRequestAssembler.classifyUserMessage()
function classifyUserMessage(message: string): 'greeting' | 'farewell' | 'career' {
  const lower = message.toLowerCase().trim();
  const greetings = ['hello', 'hi', 'hey', 'good morning', ...];
  if (greetings.some(g => lower === g || lower.startsWith(g + ' '))) return 'greeting';
  // ...
  return 'career';
}

For 'greeting' or 'farewell', the server returns a hardcoded Protocol v1.3 response object immediately — no Gemini API call, 0 tokens consumed. For career queries, the full pipeline runs.

Problem: Request amplification (D5)

Lab approach: Single primary call; no chained administrative calls during the user-facing response.

The lab makes one model call per user message on the primary path. Any secondary operations (session summarisation, context compaction) are triggered by budget thresholds, not by every response, and they use a lightweight prompt with minimal context — not the full counselling conversation.

Problem: Rate limiting and quota protection

Lab solution: Per-IP sliding window rate limiter (inline, no external dependency).

The lab implements a makeRateLimit(maxPerMinute) middleware in server.ts using an in-memory Map<string, {count, resetAt}>. Applied at 20 RPM for chat, 30 RPM for token counting, 10 RPM for benchmarks. Returns HTTP 429 with errorCode: "RATE_LIMIT" which the frontend renders with a clear "wait a moment" message — distinguishable from quota exhaustion (QUOTA_EXHAUSTED), which shows a "resumes at midnight" message.

14. Recommended Production Implementation Plan

Ordered so that each step is verifiable before the next depends on it. Nothing here conflicts with Spring AI 1.0.0 GA — all fixes use features the framework already provides.

  1. Phase 0 — Verify model identity (30 seconds)

    Read application.properties:72 on the live deploy. If still gemini-2.5-pro, this is a leading latency contributor and must be resolved before any other timing claims can be made. Change to gemini-3.5-flash-lite for counselling turns; reserve Pro for future high-stakes assessment features only.

  2. Phase 0b — Capture a browser HAR (5 minutes, no code change)

    For a ~10 s chat request: is the response chunked (streaming) or one blob at the end (buffered)? This settles the stream=false hypothesis (H2) immediately. Also count Vertex AI invocations per user message to measure the amplification factor (H1).

  3. Fix D4 — Add token telemetry (highest priority)

    Call response.getMetadata().getUsage() on every ChatResponse. Persist promptTokenCount, completionTokenCount, totalTokenCount per turn and per conversation. Log with a correlation ID. Build a simple dashboard (even a SQL query) that shows the turn-10/turn-1 input-token ratio per conversation. Without this, no other claim in this document — including these projections — can be verified.

  4. Fix D7 — Shared "default" conversation (1 line, privacy defect)

    Pass the authenticated user's conversation ID on every call path at GeminiClient.java:253. This is a privacy and correctness defect independent of all cost issues. It must not wait behind the cost programme.

  5. Fix D1 — .user() → .system() for instruction delivery (4 lines, biggest single win)

    Separate the instruction text from the student utterance. Pass the stable counselling instruction as .system(stableInstruction) and the actual student message as .user(actualStudentUtterance). This removes the quadratic term entirely. Vertex AI will route the system content to withSystemInstruction() — the field it treats as the cache-eligible header. Expected outcome: promptTokenCount ratio turn-10/turn-1 drops from ~10× to ~1.1×.

  6. Fix D2 — Token-budget ChatMemory

    Implement TokenBudgetChatMemory implementing Spring AI's ChatMemory interface. Preserve SystemMessage unconditionally. Evict oldest whole user+assistant pairs until the remaining window fits a token budget (e.g. 8,000 tokens). Never evict the stable instruction prefix. Port the lab's TokenBudgetMemoryManagerTest alongside it — it is one of only two AI tests in either codebase, and production has none.

  7. Fix D5 — Reduce/eliminate sequential chained model calls

    Audit every chatClient.prompt()...call() triggered by a single user message. For title generation and administrative classification calls, use a lightweight model (flash-lite) with a minimal 2-turn context rather than the full counselling model with full history. Parallelise where possible. Measure the amplification factor before and after using telemetry from step 3.

  8. Fix D6 — Enable true streaming (stream=true)

    Change the main client call to stream=true. Ensure PromptPlaceholderReplacer.handleResponse() works on the streaming path — the chained-call status decision must not require buffering the complete response. This is the largest single perceived-latency improvement at low risk.

  9. Fix D1b — Stable/volatile prompt split

    Fix D1 alone stops the accumulation but does not unlock caching, because the instruction text changes every turn through placeholder substitution and nextPrompt chaining. Split the instruction into: (a) stable layer — counselling methodology, tone, response contract, schema — byte-identical for every student and turn, delivered as .system(); (b) volatile layer — phase, lastAction, student profile, placeholder values — delivered as a small additional user preamble. The stable layer becomes the cacheable prefix.

  10. Fix D8 — Append-only DB persistence

    Replace the delete-all + reinsert pattern in JdbcChatMemoryRepository.saveAll() with an append-only insert. Only the new message(s) for the current turn are written. A separate trim job compacts old rows. This reduces DB writes from O(N) per turn to O(1) and eliminates the write-amplification contribution to RDS load.

  11. Fix D10 — Cache Mongo prompt fetch

    Add a checksum field to the Prompt document. Cache the fetched prompt in a ConcurrentHashMap<String, CachedPrompt> keyed by (action, checksum). Invalidate when checksum changes. Eliminates one Mongo round-trip per request.

  12. Future — Protocol v1.3 structured output

    The Token Lab validates every response against a 20,694-byte JSON schema. Production currently parses responses opportunistically for a status field only. When the counselling team is ready, adopting Protocol v1.3 would enable structured phase tracking, follow-up suggestion arrays, and service metadata — all without free-text parsing. Re-run the token cost analysis at adoption time as the schema adds per-request input cost.

15. What NOT to Copy from the Token Lab

Lab compaction is string-building, not summarisation

⚠️

Both lab compactors are string builders, not AI summarisers. The Java tier truncates messages to 60 characters. The Node tier interpolates a message count into a fixed sentence template. Neither preserves the semantic content of the conversation being compacted. Do not adopt these compaction patterns in production counselling.

The counselling product's value is the longitudinal evolution of a student's position. A rolling summary that reduces a student's 10-turn exploration of career options to "5 messages discussed career options" destroys the very substance that makes the counselling meaningful. The correct sequence is: remove the waste first (the duplicated instruction text, which was never real history), measure the remaining cost, and only then ask whether genuine conversation history needs compressing — with a real AI summariser and an explicit answer to the counselling-continuity question.

Lab cached-token figures are synthetic

The Token Lab substitutes a synthetic value when the provider returns no cached-token metadata: 45% of input tokens in server.ts:978, a flat 55% in GeminiChatService.java:193. These are hardcoded guesses reported through the same field as a real measured value. Do not use any cached-token figure from the lab as evidence of caching effectiveness in production. Cache effectiveness in production can only be inferred from billed input cost against the stable-prefix change, and should be labelled as an inference.

Lab Spring backend is a simulator, not a reference

The lab's Spring tier (GeminiChatService.java:175,182) makes no model call. It splits a pre-built JSON payload and emits it with Thread.sleep(15) per chunk. A 4,000-character response produces 12 seconds of pure artificial delay with zero provider latency. Any timing data attributed to the lab's Spring backend is 100% manufactured. Use only the lab's Node.js tier (server.ts) for latency evidence, and only when the server is confirmed to be using generateContentStream.

Lab per-message model display is a lab-only feature

The per-bubble model chip, latency display, and token pill in the lab UI are instrumentation tools for the lab's purpose of demonstrating and comparing model behaviours. Production does not expose these to end users (students) — only to the engineering dashboard and internal monitoring.
